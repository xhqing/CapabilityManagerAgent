# 底层通用能力开源与镜像同步

> 本文件由全局 `~/.pi/agent/CLAUDE.md`「团队结构参考」指针节指向。**何时读**：维护全局 `~/.pi/agent/` 的通用能力（skills / CLAUDE.md / docs / patch / pi 扩展）时、装 / 删 / 升级 pi 第三方包后刷新清单时、同步 CapabilityManagerAgent `pi/agent/` 镜像时。权威源在全局 `~/.pi/agent/`，开源镜像在 CapabilityManagerAgent 仓库 `pi/agent/`（路径一一对应）。

## 全局权威 ↔ 本项目镜像，内容时刻一致

> **2026-10-17 权威源迁移**：全局权威源已由 `~/.claude/` 迁至 **`~/.pi/agent/`**（真实文件：`CLAUDE.md` / `skills/` / `docs/` / `patch/`；裸 `hooks/` 目录名在 pi 中已废弃——被 pi 扩展调用的辅助脚本统一放 `patch/` 下，如 `patch/settle-repo-check/`）。原 `~/.claude/hooks/` 的 CC 系脚本为遗留、不再随 pi 维护。
>
> **2026-10-22 镜像结构迁移（用户决定）**：团队已全面转向 pi-harness，镜像结构同步对齐——原 `claude/` 目录（`skills/` / `CLAUDE.md` / `docs/` / `patch/` / 历史遗留 `hooks/`）整体迁入 `pi/agent/` 下对应路径，`hooks/` 不迁移（CC 遗留，直接删除），`claude/` 目录随后删除。此后不再有 `claude/` 镜像；所有通用能力镜像统一在 `pi/agent/` 下。

CapabilityManagerAgent（Prometheus）是把智能体团队的**底层通用能力底座开源出去**的源头仓库。**全局 `~/.pi/agent/`（含 extensions）是通用能力的权威源**；该项目 `pi/agent/` 下对应的部分——`skills/`、`CLAUDE.md`、`docs/`、`patch/`、`extensions/`——加上 `pi/agent/npm/` 的生成式清单，是全局权威源的**开源镜像**（原 `rules/` 五条规则已全文并入 CLAUDE.md，rules/ 目录已删除，历史版本见该仓库 git 历史），必须与全局**时刻保持逐字节一致**。

- **目录布局**：该项目 `pi/agent/` 目录就是全局 `~/.pi/agent/`（五部分 + 生成式清单）的开源镜像，路径一一对应：`~/.pi/agent/skills/` ↔ `pi/agent/skills/`、`~/.pi/agent/CLAUDE.md` ↔ `pi/agent/CLAUDE.md`、`~/.pi/agent/docs/` ↔ `pi/agent/docs/`、`~/.pi/agent/patch/` ↔ `pi/agent/patch/`、`~/.pi/agent/extensions/` ↔ `pi/agent/extensions/`、`~/.pi/agent/npm/` 清单 ↔ `pi/agent/npm/`。该项目运行时**只加载全局 `~/.pi/agent/`**，不加载镜像副本（镜像只是开源出口、不是运行依赖）。项目根 `.claude/` 目录保留为该项目**独有的项目级能力目录**，放该项目特有、不随通用能力同步的内容（如 capability-manager skill——Prometheus 本项目的专属工具）。
- **权威方向**：**全局 `~/.pi/agent/` 是唯一权威源**，该项目 `pi/agent/` 对应部分是它的镜像。改动先在全局落地（全局是所有项目运行时实际加载的「活」源头），再同步覆盖到该项目 `pi/agent/` 镜像；反过来不准只改镜像而不动全局（那样镜像会与权威源分叉）。**为什么以全局为权威**：全局是实际运行时加载的中心、是「活」的；镜像只是把全局内容开源出去的快照，以全局为权威更贴合实际使用，也避免了「权威源不被加载、要靠镜像回流」的别扭。
- **范围（五部分 + 生成式清单）**：`skills/` 下所有**通用** skill、根 `CLAUDE.md`（含已并入的「工作规则」五条）、`docs/` 下拆出的参考文档（agents-registry、new-agent-scaffold、capability-sync、ark-key-pool 等）、被 pi 扩展调用的辅助脚本与自研机制（`patch/` 下：`settle-repo-check/`、`skill-custom/`、`session-sweep/`、`npm-manifest/`、`session-link/`、`duty-macmini/`、`sync-to-macmini/` 等——目录取名 `patch` 即「自研补丁 / 增强层」，放进去即公开）、pi 扩展（`~/.pi/agent/extensions/` 下的工具强制 / 机制类扩展，数量以目录实际为准；**项目专用扩展不纳入镜像**——判定标准：含特定项目硬编码路径、或仅单项目会话激活的机制，clone 者用之无意义、且会带出项目工作流细节；如需纳入应先改造为通用形式）。这五部分在全局是权威、在该项目是镜像（`~/.pi/agent/` 的 skills / CLAUDE.md / docs / patch / extensions 五部分 ↔ `pi/agent/` 下同名路径），逐字节相同。**另有第六类（生成式清单）**：pi 在用**第三方** npm 包的备份清单——`~/.pi/agent/npm/` 的 `package.json`、`package-lock.json`（pi 自动维护）加生成的人读清单 `PACKAGES.md`，由 `patch/npm-manifest/refresh.py` 刷新同步到该项目 `pi/agent/npm/`；用途是**本机在用能力的备份与迁移**（换新机器按清单精确重建），与源码镜像不同：**不放第三方包内容**（体积 / 平台耦合 / 更新成本），只放声明、精确锁与清单，属**生成式内容**（校验用脚本 `--check`，不做逐字节 diff）。**不含 `commands/`**（各处 commands 自行管理）；**不含项目级专属 skill**（如 capability-manager，放 `.claude/`、不进通用同步）；**不含镜像对象目录下的运行时 / 编辑产物**（`patch/` 的 `*.log`、`.lock`、`conflicts/`、`__pycache__/`——本机产物，不进镜像）。
- **特例（2026-10-18 立）：`diff-view.ts` 的源头在项目侧**：pi「改动可视化」已整合为 Kit 名下子项目 diff-view——pi 侧组件源码在 `~/Developer/diff-view/diff-view-pie/diff-view.ts`，全局 `~/.pi/agent/extensions/diff-view.ts` 是该项目的 `install.sh` 部署副本（clone 者按同法安装）；VS Code 侧组件（`diff-view-vsce`）随项目分发、不进全局能力层与镜像。镜像照旧同步全局这份部署副本，逐字节一致的要求不变（全局副本 ↔ `pi/agent/extensions/diff-view.ts`）。
- **特例（2026-10-22 立）：`ark-key-pool.ts` 的源头在项目侧**：Kit 名下子项目 `~/Developer/ark-key-pool/ark-key-pool.ts` 是源码，全局 `~/.pi/agent/extensions/ark-key-pool.ts` 是该项目的 `install.sh` 部署副本；镜像照旧同步全局这份部署副本，逐字节一致的要求不变（全局副本 ↔ `pi/agent/extensions/ark-key-pool.ts`）。
- **唯一例外：敏感信息**。涉及密钥、凭证、本机运行数据的内容（如 `settings.local.json`、`skills/anysearch/.env`、`skills/backup/endpoints/*`、`patch/session-link/*.json` 等本机配置），不在「逐字节一致」的硬要求内——由该项目用 `.gitignore` 在项目级隔离，确保敏感信息不随开源仓库泄露。除此之外**不存在任何特例**：包括 `runtime.conf` 路径也不特殊对待，项目副本与全局逐字节相同，clone 者拿到后按本机路径自行适配即可。
- **为什么**：把全局钉成权威源（实际运行时的中心），`pi/agent/` 作为开源镜像，任何人 clone 该项目即得通用能力快照；全局改一处、镜像同步一处，避免两边分叉、互相漂移。
- **怎么验证**：每次改动后用 `diff -r ~/.pi/agent/<部分> pi/agent/<部分>`（skills / docs / patch / extensions）与 `diff ~/.pi/agent/CLAUDE.md pi/agent/CLAUDE.md` 核对五部分是否仍逐字节一致（被 `.gitignore` 隔离的敏感文件、镜像对象目录下的本机产物与项目专用扩展不参与公开比对，是仅有的允许差异；核对 patch 时用 `diff -r -x '*.log' -x '.lock' -x 'conflicts' -x '__pycache__' ~/.pi/agent/patch pi/agent/patch` 排除本机产物）。**另需确认这几部分在 git 里是「已跟踪」状态**：`git ls-files pi/agent/docs | wc -l` 等不应为 0（或 `git check-ignore -v <文件>` 应无输出）——2026-10-04 事故：镜像仓库 `.gitignore` 里一条**裸 `docs/`** 规则把镜像 docs 静默吞掉，本地 `diff` 全绿、远端却少了一整部分（docs 从未发布过），只靠 diff 发现不了。npm 清单（第六类）用 `python3 ~/.pi/agent/patch/npm-manifest/refresh.py --check` 核对镜像与当前本机是否一致（生成式内容，不参与逐字节比对）。
- **追加 CHANGELOG 条目后的自查**：新条目必须落在**当前日期节**内（其行号在下一个日期标题之前），且日期标题不重复（如 `grep -c '^## 2026-10-12$' CHANGELOG.md` 应为 1）——2026-10-12 两批镜像同步曾两次把新条目插到上一日期节下、并重复日期标题（均被 Prometheus 修正）：成因是插入锚点处把日期标题重写了一遍；正确写法是「新条目 + 原锚点文本原样」，不要在插入内容前重复锚点标题。
- **自动同步、无需每次询问**：一旦发现全局 `~/.pi/agent/` 和该项目 `pi/agent/` 镜像之间出现分叉（无论哪边领先），**直接自动同步对齐，不要再向用户询问「要不要同步」**。同步方向以全局权威优先——理想流程是改动先落全局、再镜像 `pi/agent/`；若分叉是镜像领先（比如临时直接改了镜像），就把镜像内容覆盖回全局、一次性对齐后，继续走全局优先。装 / 删 / 升级 pi 第三方包后，同样自动跑 `refresh.py` 刷新 npm 清单（不问用户），并按规矩记本项目 CHANGELOG。
- **同步动作只记 CapabilityManagerAgent 的 CHANGELOG**：通用能力同步这件事本身的变更记录，**只记在 CapabilityManagerAgent 的 `CHANGELOG.md`**，**不记到其它任何项目的 CHANGELOG**（如各业务项目 DayTradingAgent 等）。为什么：底层通用能力的同步归这个开源仓库管、是它本身的事，不该混进各业务项目自己的变更记录里、污染那些项目的 changelog。
