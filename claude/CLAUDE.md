# User Preferences

## Language

- 默认使用**简体中文**回答用户。除非用户明确要求使用其他语言，或上下文明显需要用其他语言（如代码注释、英文技术术语、引用英文原文），否则所有回复均使用简体中文。
- 行文使用**标准、地道的普通话**，选用通用的规范词汇，避免生僻、生硬或带翻译腔的措辞，不使用少见词。
- 回复**排版工整**：标题层级清晰，列表规整，段落之间空行分隔，代码块与表格格式正确，便于阅读。
- 标点符号一律使用**简体中文标点**：逗号用「，」、句号用「。」、冒号用「：」、顿号用「、」、问号用「？」、感叹号用「！」，不要用英文标点（如 `,` `.` `:` `?` `!`）。中英文混排时，英文单词或数字与中文之间可留一个空格，但中文语句内部一律用中文标点。
- **缩写约定**：用户输入「**CC**」即指 Claude Code，输入「**VSC**」即指 VSCode，输入「**VSCE**」即指 VSCode 扩展，输入「**CB**」即指 CodeBuddy，输入「**GH**」即指 GitHub，输入「**DSH**」即指 DeepSeek Harness（DeepSeek 开源的 agent harness，npm 包 `@deepseek-ai/dsh`，2026-08-21 立）。缩写**大小写不敏感**——大写「CC / VSC / VSCE / CB / GH / DSH」与对应小写「cc / vsc / vsce / cb / gh / dsh」同义（如「cc 会话」= Claude Code 会话、「gh 仓库」= GitHub 仓库、「dsh 安装」= 安装 DeepSeek Harness）。遇到这些缩写时直接按此解读，无需再向用户确认。解读均以不影响上下文理解为前提——若某缩写在上下文中明显指别的含义，按上下文实际含义辨别（典型如小写 `gh` 出现在命令位置时指 GitHub CLI 命令、`cc` 在编译器语境指 C 编译器、`dsh` 在分布式 shell 语境指 Dancer's shell / distributed shell，均不按上述缩写解读）。

## 输出风格（2026-07-14 用户修订）

**总原则**：用规范的通用术语表达，不为了短而自创简写；语义清晰始终是底线（不为短牺牲语义，也不为凑字数啰嗦）。**默认用大白话把逻辑、前因后果解释清楚**（写入文件、复盘、一般对话都走这条）；**唯独「盯盘的对话输出」是特例，排除在大白话详细解释之外——要精简、高信息密度**（盘面秒变，长篇解释会让用户收到时情况已变、结论失配）。

- **写入文件（skill / rules / 文档）**：不考虑信息密度，用最标准的普通话大白话把逻辑解释清楚，宁可多用文字也要让人一遍读懂。
- **复盘、一般对话**：不追求精简，用大白话把事情说清楚，可以详细展开。
- **盯盘的对话输出（特例，唯一要精简的场景）**：结论直接给、信号直接发、不展开解释，但仍然要语义清晰、容易理解。
- **不要自创简写**（所有场景通用，含盯盘）：通用术语（行业惯用词、技术名词、既有缩写如 CC / VSC）正常使用，但不为了短而自造缩略说法（例如把「买盘较多」压成「偏正」、把「继续上涨」压成「续涨」）。
- **逐条检测 / 核对类结果用 ✅ / ❌ 列表展示**（所有场景通用，2026-07-16 用户立）：回复中凡是「多条检测项逐条判断是否通过 / 就绪」的结果——例如 /commit 第 9 步项目标配检测、add 前的敏感内容扫描 + cache 检测、文件改完后的验证清单等——一律用列表逐条展示，**通过的打绿勾 ✅、没通过的打叉 ❌**（形如 `- ✅ License：已存在`、`- ❌ GitHub About：未配 topics`），不要用表格、不要用整段文字罗列。原因：✅ / ❌ 一眼就能看到每条的通过状态，比表格或密集段落更容易扫读。不适用于盯盘实时信号输出和纯叙述性回复。

## 文件命名规范（2026-08-10 用户立）

凡新建文件（代码、文档、脚本、配置、缓存等一律适用），**文件名必须用英文命名**（ASCII 字符），**且必须用尽可能简单的名字**——简短、直接、不带冗余修饰词。例如 commit skill 的检测缓存文件原名为 `.commit-skill-cache.md`，其中 `skill` 是冗余修饰，简化为 `.commit-cache.md`。

- **怎么用**：命名时先写出全名，再逐词检查每个词是否必要——纯修饰性、与上下文重复（如目录名已表达的信息）的词一律删掉，直到删无可删。
- **边界**：「尽可能简单」以**不牺牲语义清晰**为底线（与「输出风格」节「不为短牺牲语义」同原则）——命名必须让人一眼看出文件用途，压到语义不明（如把 `README.md` 压成 `R.md`）就是过度简化，不允许。
- **存量文件**：已有文件的简化改名按同样规则处理，改名时同步更新所有引用处（代码、文档、skill 正文等）。

## 表述的逻辑严谨性（重中之重，2026-07-15 用户立）

**表述的逻辑严谨性是重中之重，优先级高于本文件里所有关于「怎么说」的规则（精简、大白话、信息密度等）——遇到冲突，先保证逻辑严谨。** 一条结论如果逻辑不严谨（以偏概全、外推不留边界、数学关系含糊、自相矛盾），哪怕说得再精简漂亮，也是错的、会误导决策。具体要求：

- **经验教训总结的目的就是为了泛化（提炼可复用的普遍规律），不是仅仅记录特例**——只记录特例而不提炼规律，总结就失去了价值；不能因为怕泛化出错就停留在就事论事。**但泛化必须严谨、保证逻辑完备**：由特例外推到普遍规律时，要理清特例与普遍规律的关系和异同、明确规律的适用条件与边界（在什么情况下成立、什么情况下不成立），并尽量多考虑一些情况来验证规律的完备性。错误不在「泛化」本身，而在「不加限定地全称外推」——比如从「这组止损参数下 SOXL 赔率低于 MU」直接跳到「杠杆让赔率降低」，既没说明适用条件、也没覆盖其他参数；正确做法是提炼出「杠杆同时推大止盈和止损空间、赔率升降取决于两者放大倍数」这条普遍规律，同时把「常见止损宽度下 SOXL 与 MU 谁赔率高」标注为「取决于具体参数、需实算」。（2026-07-15 用户三次纠正后修订。）
- **数值结论必须实算，不许凭直觉断言**。涉及比较、比例、倍数、大小关系的结论，把具体数字代进去算一遍再下结论；算不清就改用不确定语气（「印象中……待核实」），不要硬给一个定律式的断言。
- **数学关系要表述精确**。比如「分子分母同时放大」不等于「比值降低」——比值升降取决于两者放大倍数孰大（同倍不变 / 分子大则升 / 分母大则降）。含糊表述比不说更糟。
- **查证外部行为先找官方文档，本地实验只做补充验证（2026-08-22 用户立）**。要回答「某个系统 / 服务 / 工具的行为规则是什么」（API 参数语义、档位映射、配置默认值、协议字段含义等），第一步是查官方文档——官方文档是权威承诺，本地实验只是自己环境下的单点观察（样本 n=1、有噪声、可能随版本变化）。顺序错了就是本末倒置：先做实验、拿实验结果当普遍规律下结论，即便碰巧对了也只是没被证伪的猜测。**为什么**：2026-08-22 在 CC-BRIDGE 判断「GLM 端点如何解读 CC 的 effort 档」时，我先对端点做了一轮本地 A/B 实验就下了结论，用户指出「不如去搜索官方文档」——官方文档里本就有明文映射表（且顺带给出「默认档即 max」等实验没覆盖的关键信息），实验结论只是与文档一致的旁证。**怎么用**：① 遇到此类问题先搜 / 读官方文档，文档有明文就以文档为准；② 文档查不到（未公开、过时、需区分版本）才做本地实验，且实验结论要标注「本地实测、n=1、可能与官方未公开行为有出入」；③ 文档与实验冲突时以文档为准，实验只用来发现「文档没写」或「文档与实际不符（可反馈官方）」的增量。**边界**：本条管「外部系统行为规则」的查证顺序；用户自己的代码 / 项目行为（无官方文档可言）当然靠读源码与实测，不受本条约束。

## 不主动进入 Plan 模式（2026-07-17 用户立）

**不要主动调用 `EnterPlanMode` 进入 plan 模式**。接到任务（包括复杂、多文件、涉及架构的实现类任务）时，直接读代码、动手做，**不要**先切到 plan 模式走「探索 → 给方案 → 等审批」的流程。

- **为什么**：用户有自己的规划方式，不希望被强制进 plan 模式打断；plan 模式会把会话锁成只读、增加来回沟通、拖慢节奏。用户更希望 Agent 直接干活，方向不对再调整，而不是每次先停下来等审批。
- **怎么用**：
  - 实现类任务直接开干——读代码、改文件、跑验证，按部就班推进，不调用 `EnterPlanMode`。
  - 如果确实需要先和用户对齐方向（比如方案分叉大、改完返工成本高），在**普通回复里用文字**说清楚「我打算这么做，理由是……」，等用户回应，**不要**切到 plan 模式走正式审批流程。
  - 用户主动说「先规划一下」「给个方案」时，用文字给方案即可，仍不必走 plan 模式；只有用户明确要 plan 模式时才用。
- **与配置互为双保险**：本条与全局 `~/.claude/settings.json` 里 `permissions.deny` 已加入的 `"EnterPlanMode"` 配合——**配置层把工具整个移除（硬约束）、指令层要求不主动用（软约束）**。两者叠加：即便将来某版本配置层 deny 对这个内部工具失效，指令层仍兜底提醒不主动进 plan。
- **边界**：本条只约束 Agent 的**主动**行为；用户自己用 shift+tab 手动切到 plan 模式不受影响。指令层非硬强制（CLAUDE.md 指令 Agent 会尽量遵守但无法 100% 保证），真正的硬约束靠配置层的 deny。

## Git 写操作必须先征得同意（2026-07-13 用户立）

**未经用户明确同意，禁止执行任何会改动仓库的 git 命令**：`git add`、`git commit`（**仅限用户主动 `/commit` 触发、不走本节「先征得同意」**，详见下文「Git 暂存区禁止 AI 自主增删改」节）、`git push`、`git rm`、`git mv`、`git reset`、`git revert`、`git rebase`、`git merge`、`git cherry-pick`、`git tag` 等。**每次执行前必须先列出：具体命令 + 影响的仓库 + 改动摘要，等用户点头再执行。**

- **为什么**：用户要对每一次提交 / 推送 / 历史改动亲自把关，避免未经审阅就改动仓库或推到远端。
- **怎么用**：即便用户给了「开源到 GitHub」「提交一下」「推一下」之类大方向指令，也**不能据此直接动手**——仍要逐次把命令列清楚、等确认。哪怕已经授权过一次，下一次仍要重新询问（授权不跨次复用）。
- **不受限**：只读操作（`git status` / `git diff` / `git log` / `git show` / `git branch` / `git remote -v` 等）无需询问。
- **新建项目 `git init` 免确认（2026-07-16 用户立）**：凡是新建项目（含 agent 项目），默认都用 `git init` 做本地初始化——项目默认就是 git 项目，**本地初始化即可、不创建远程仓库、不 push**。`git init` 只在项目内创建 `.git`、不改动任何现有仓库，故新建项目时直接执行、无需每次询问。**边界**：免确认仅限 `git init` 本身；其后的 `git add` / `commit` / `push` / 建远程仓库 / 打 tag 等仍按上方规则需先确认（或由 `/commit`、`/release` 触发）。
- **例外（`/commit`、`/release` 等用户主动触发的提交 / 发布类 skill）**：用户主动输入 `/commit`（commit skill）即**明确授权**当次的 `git commit` + `git push`（不执行 `git add`，只提交用户已自行 `git add` 到暂存区的内容）；用户主动输入 `/release`（release skill）即**明确授权**当次的 `git tag -a` + `git push origin <tag>` + `gh release create`。两者均应**直接执行**完整流程，**无需再列命令等确认**。上方「逐次确认」规则针对的是**我（Agent）自主发起的** git 写操作（怕擅自提交 / 打 tag / 发版），**不适用于用户主动触发的 `/commit`、`/release`**——用户发这类命令就是要一键完成，再问一遍是多余的反 confirm。`/commit` 仅在敏感扫描或 cache 检测命中时**终止**（不暂停续跑，详见下「commit skill 的触发与终止」段）；`/release` 在 tag 已存在、工作区脏、CHANGELOG 缺条目、Release 已存在等异常时暂停（详见 release skill）。
- **`/release` 即授权发布构建产物，不再问要不要产物（2026-07-17 用户立）**：`/release` 的核心目的之一就是**发布构建产物**（VSCode 扩展的 vsix、可执行包、压缩包等 Release asset）。用户输入 `/release` 即**明确授权「构建并上传构建产物」**——直接构建（如 `npm run package`、`npx @vscode/vsce package`）并作为 asset 上传到该 Release，**不再用 AskUserQuestion 问「要不要构建 / 上传产物」**（再问是多余的反 confirm，与本段「例外」同理）。即便构建需绕过工具限制（如 `vsce` 禁止 README 引用本地 SVG、检测不到仓库 URL、会把 `.claude/` 等本机配置打进包），也**直接用打包工艺解决**（临时中转 README、打包期间临时移走 `.claude/`、补 `--baseContentUrl` / `--allow-missing-repository` 等），不因「要不要产物」打断流程；构建失败则如实报告。**边界**：本条只免除「要不要构建 / 上传产物」的询问，不扩展到 release skill 的其它异常安全阀——tag 已存在、Release 已存在、工作区脏、CHANGELOG 缺条目、版本号异常等仍按 release skill 暂停询问，不因本条跳过。

## Git 暂存区禁止 AI 自主增删改（2026-08-02 用户立，硬性规定）

AI 对 git 暂存区（staging area / index）的操作，按「能否自主做」严格分三层：

1. **AI 能自主做的：只有只读查询**——`git status`、`git diff`、`git diff --cached`、`git log`、`git show`、`git ls-files`、`git branch`、`git stash list` 等。AI 可自行执行，无需授权。
2. **需用户明确授权才能做：`git commit`**——把用户已自行 `git add` 到暂存区的内容提交到本地仓库。**commit 必须在用户发出明确授权后才能做，而 commit 的明确授权 = 用户主动发起 `/commit` 命令**（口头说「提交一下」「commit 吧」、或对 AI 列出的 commit 命令点头，都不算明确授权，AI 不得执行）。commit 提交后暂存区清空是 commit 的固有行为，不属于 AI 对暂存区的增删改。
3. **禁止（无论是否授权，一律不得执行）：对暂存区的任何增、删、改（含移动）**：
   - **增**：`git add`、`git stage`（往暂存区加入内容）。
   - **删**：`git rm --cached`、`git reset HEAD <file>`、`git restore --staged <file>`、影响暂存区的 `git reset`（如 `--hard` / `--mixed` / 默认 reset）（从暂存区移除或重置内容）。
   - **改 / 移动**：`git mv`（移动 / 重命名会同步改暂存区）、任何会改变暂存区现有内容的命令。

- **为什么**：暂存区的内容由用户亲自 `git add` 把关，反映用户精心挑选的「本次要提交什么」。AI 自主对暂存区增删改（含移动）会篡改用户的选择——把不该提交的塞进提交、或把该提交的弄丢。把暂存区钉成「AI 自主只能只读、commit 需用户明确授权（发起 `/commit`）、增删改含移动一律禁止」，确保提交内容完全由用户掌控：暂存区里放什么、何时提交，都由用户亲自决定（`git add` 与 `/commit` 都是用户主动发起），AI 永不替用户改动暂存区、也不擅自提交。
- **与「Git 写操作必须先征得同意」的关系**：本条针对「暂存区」这一特定对象，比上一节「先征得同意」更严——即便用户授权了某次 git 操作，只要它属于对暂存区的增删改（含移动），**仍然禁止**。`git commit` 不走上一节的「先征得同意」（列命令等点头），其唯一授权入口是用户主动发起 `/commit`（见上方第 2 层）。上一节「/commit 不执行 git add、只 commit 用户已 add 的内容」正是本条的体现；本条把它推广为针对暂存区的普适硬约束。
- **边界**：本条只约束「对暂存区的操作」；工作区的普通文件操作（`mv`、`rm`、编辑文件等，不经 git）不受本条限制（仍受「文件操作优先级规则」等约束）。`git reset --soft`（只移 HEAD、不动暂存区）不在本条禁止范围，但仍属「改仓库历史」类、受上一节「先征得同意」约束。

## 敏感信息禁止写入未被 .gitignore 忽略的文件（2026-08-02 用户立，2026-08-26 增补财务状况，硬性规定）

任何敏感信息——券商 / 银行账户号、API key、token、密码、私钥、数据库连接串、个人隐私标识、**个人 / 公司 / 组织的财务状况**（收入目标与实际收入、本金、资产、负债、存款、财务紧迫程度、职业投入状态等描述性信息，2026-08-26 增补）等——**一律不得写入任何未被 `.gitignore` 忽略的文件**（即会被 git 跟踪、可能进仓库的文件），无论文件类型（代码、文档、CHANGELOG、TODO、skill 正文、README、复盘等）、无论该文件当前是否已提交。

- **为什么**：2026-08-02 事故——在 `CHANGELOG.md` / `TODO.md` 记录「老虎 paper 账户号恢复接入」过程时，把 17 位模拟账户号与 7 位实盘账户号明文写进公开仓库文档，靠 `/commit` 敏感内容扫描才发现并终止提交。敏感信息一旦进入 git 历史就是永久明文（本次两个号正是从脱敏前的旧 commit 明文恢复出来的），改文档、删文件都洗不掉。**`/commit` 的敏感内容扫描只是最后一道防线，不是第一道**——正确姿势是「写的时候就不写」，不能先写进文件、再指望扫描拦截。2026-08-26 事故（增补财务状况类型的起因）——ExecutiveAssistantAgent 的 CHANGELOG 在记录新建投标 SOP 文档的原因时，写入了用户的收入目标、本金状况、财务紧迫程度与全职投入状态等个人财务状况描述，随开源仓库公开并进入 git 历史，最终被迫用 `git filter-repo` 重写全部历史 + force push 才能清除。财务状况描述与账户号 / 密钥不同：它不是凭证、没有占位符可填，写数字不行、写占位符也没有意义——唯一的正确姿势是**整体不写**。
- **怎么用**：
  - 写任何文件前先判断：这个文件会被 git 跟踪吗？会 → 敏感信息一律用占位符（如 `<HK_PAPER_ACCOUNT>`、`<API_KEY>`）或「真实值见本机配置」的表述代替；真实值只写进本机文件（`.gitignore` 忽略的配置、环境变量、secrets）。
  - **财务状况类信息没有占位符可用，处理方式是整体不写**：文档里写「为什么做某事」时，只陈述业务目标与方法论（如「为沉淀接单方法论、建立获客路径」），不写背后的收入目标（月入 X 元）、本金状况（零 / 低本金 / 手头紧）、财务紧迫性（燃眉之急、解决生计）、投入状态（全职 / 兼职 / 无其它收入）等财务背景。确需记录财务背景供自己复盘的，写入被 `.gitignore` 忽略的本机文档（`docs/` 等运行时数据目录），不进 git 跟踪的文件。
  - 记录类文档（CHANGELOG、TODO、复盘、README）描述涉及敏感信息的过程时，同样只写占位符 + 说明「真实值在本机配置 / git 历史」，不写数字本身——用「17 位模拟账户号」表述即可，不必带具体号码。
  - 拿不准某信息是否敏感 → 按敏感处理，宁可写占位符（财务状况类则宁可整体不写）。
  - `/commit` 前的敏感内容扫描与 cache 检测照常保留作兜底，但依赖它拦截 = 已经违规到仓库边缘。
- **边界**：本条只约束「会被 git 跟踪的文件」；已被 `.gitignore` 忽略的本机文件（密钥、配置、env 等）不受限。

## 「发布」「最新版」默认指 GitHub Release（2026-07-19 用户立）

凡用户提到「发布」「已发布」「发版」「最新版」「升级到最新版」「装最新版」等词、且**未指明渠道**时，**默认指 GitHub Release**（即 `gh release create` 打出的 tag + Release，含挂在 Release 上的 vsix、二进制等构建产物），**不是** VSCode Marketplace、也不是 Open VSX。

- **为什么**：用户的产物（如 RM 这类 VSCode 扩展）大多通过 GitHub Release 分发 vsix，并未上架公共 Marketplace；「发布 / 发版」在用户语境里就是打 tag 发 Release。把默认渠道钉死成 GitHub Release，省得我每次都去 Marketplace / Open VSX 白查一遍、或擅自理解成别的渠道走错路。
- **怎么用**：
  - **升级已安装扩展到最新版**：先 `gh release view -R <owner>/<repo>` 看最新 tag 与 assets，从最新 Release 下 vsix，再 `code --install-extension <vsix> --force` 覆盖安装。
  - **发布 / 发版**：走 release skill（打 tag + `gh release create` + 挂 vsix 等构建产物）。
  - 仅当用户**明确**说「发到 Marketplace」「上架 Marketplace」「Open VSX」时，才按对应市场处理。
- **边界**：
  - **适用范围限定（2026-08-01 用户修订）**：「默认指 GitHub Release」**只适用于用户自己的项目**（因为用户自己的项目目前只发布到 GitHub Release）；**别人的项目不套用此默认**——查「最新版 / 是否已发布」时，按该项目的实际发布渠道（如官方 Marketplace、Open VSX、官网等）判断，不默认往 GitHub Release 上靠。
  - 本条只定「未指定渠道时的默认值」；用户一旦明确指定了别的渠道（Marketplace / Open VSX / 私有源等），按指定的来。
  - 本条也不限于 VSCode 扩展——**用户自己项目里**的脚本、二进制等其它产物的「最新版」同理从对应仓库的 GitHub Release 取。

## commit skill 的触发与终止（2026-07-15 用户立）

- **只能由用户当前 `/commit` 指令触发**：
  - **只看当前指令、不看历史**：当前这条用户消息含 `/commit` 才考虑触发；**历史消息**里出现过 `/commit` **不触发**（不因对话历史里有 `/commit` 就续跑或重跑）。
  - **当前指令含 `/commit` 仍要先理解意图**：即便当前消息字面含 `/commit`，也要先判断意图是否真的是「现在执行提交」——若是在讨论 `/commit` 命令、举例、引用，或意图明显不是提交（例如「这条指令包含 /commit 但不是要 commit」），则**不触发**。
  - 任何疑似误触、续跑、自动触发都不执行；只有「用户当下明确要执行 commit」才走该流程。
- **命中即彻底终止，不暂停续跑**：`/commit` 流程中一旦命中敏感内容扫描或 cache 检测，**立即终止本次流程**（不 `commit` / `push`），**不存在「暂停 → 等用户处理 → 从断点继续」**。要再次提交，用户须**重新输入 `/commit`** 从头走完整流程。

## 版本信息一致性（VERSION 文件为唯一权威，2026-07-19 用户立）

凡项目根目录存在 `VERSION` 文件，该文件就是整个项目版本号的**唯一权威来源**。项目内**所有**涉及版本信息的文件——含但不限于 `package.json` 的 `version` 字段、CHANGELOG、README 徽章与正文、VSCode 扩展的 `package.nls.json` 与构建产物命名等——其标称的版本号，都必须与 `VERSION` 里的版本号**核心数字一致**。

- **允许前缀差异**：版本号前的修饰性前缀不计入比对。例如 `VERSION` 里是 `1.2.3`，那么 `v1.2.3`、`Version 1.2.3`、`"version": "1.2.3"` 都算一致——前导的 `v`、`Version `、`"version": "` 等文字 / 标点 / 引号允许不同，但核心的 `1.2.3` 三段数字（major.minor.patch）必须逐一相同。
- **为什么**：单一权威源避免版本号在各处对不上——发版时打错 tag、徽章漏更新、CHANGELOG 与 package.json 脱节都源于此；把 `VERSION` 钉成唯一源，所有地方向它看齐，一致性可机械核对。
- **怎么用**：
  - `/commit` 流程会做版本号一致性检测（详见 commit skill）：项目根有 `VERSION` 文件才查，各文件版本号与 `VERSION` 不一致即**彻底终止**本次提交。
  - 平时手动改版本号（升版本、加 beta 标记）时，以 `VERSION` 为准同步更新所有引用处，不要只改一处；改之前先改 `VERSION` 再同步其它，避免基线漂移。
- **边界**：
  - **`VERSION` 文件为项目标配**（2026-08-03 用户立：任何项目都必须有 `CHANGELOG.md` 与 `VERSION` 两个文件，缺失由 commit skill 第 9m 步自动新建）——本规则对任何项目都生效，不存在「没有 `VERSION` 就不受约束」的情况。
  - 版本号**后缀**（`-beta`、`-rc.1`、`+build` 等 pre-release / build metadata）不属于「前缀」，不自动豁免——出现后缀差异时需判断是否为有意区分（如 beta 与正式通道版本不同），不能默认视为一致。

## 版本发布状态必须实测 GitHub Release（2026-07-27 用户立）

凡需要判断「某个特定版本是否已发布」——无论是决定把新改动记进哪个 CHANGELOG 条目、判断某版本号是否可用、还是回答「X 版本发了吗」——**必须实测 GitHub Release**，**不许凭 commit 历史、VERSION 文件、CHANGELOG 条目或 package.json 版本号推断发布状态**。

- **为什么**：VERSION / package.json 的版本号会在**发版前**就 bump（属开发中状态），CHANGELOG 也会提前写好条目，commit 历史里「bump to X.Y.Z」只说明版本号改了、**不等于已发布**。唯一能确定「已发布」的证据，是 GitHub 上存在该 tag 对应的 Release。凭上述任一间接信号下结论，会把已发布版本误判成未发布（反之亦然），导致把新改动塞进已定稿的 CHANGELOG 条目、或重复发版。（2026-07-27 在 CC-BRIDGE 把 `start` 改后台时，因轻信会话开头 git log 快照「最新提交是 bump to 2.1.1」就断定 2.1.2 未发布、把改动塞进已发布的 2.1.2 条目，被用户纠正——根因正是没去查 Release。）
- **怎么用**：
  - 判断版本 X.Y.Z 是否已发布 → 跑 `gh release view vX.Y.Z -R <owner>/<repo>`：返回 Release 详情即**已发布**；报 `not found` 即**未发布**。或 `gh release list -R <owner>/<repo>` 看全部已发布版本。
  - 以 `git tag -l "vX.Y.Z"` 作为旁证（tag 存在 + Release 存在 = 完整发布）。
  - **不得用作发布判据**：「VERSION 文件是不是 X.Y.Z」「CHANGELOG 有没有 X.Y.Z 条目」「最近某条 commit 是不是 bump to X.Y.Z」「工作区有没有未提交改动」——这些在发版前就会就位，是必要不充分条件，看了也不能下「已 / 未发布」的结论。
- **边界**：本条针对「某版本**是否已发布**」的判定；版本号本身的取值仍以 VERSION 文件为唯一权威（见上条「版本信息一致性」），两者不冲突——**版本号取值看 VERSION，发布状态看 GitHub Release**。

## CHANGELOG 记录纪律（每次增删改查必记 + 防回归，2026-07-30 用户立）

项目根有 `CHANGELOG.md` 时，**每一次文件增删改查操作**（含新建、编辑、重命名、删除文件，以及对 skill / rules / 配置 / 文档的内容变更）都必须在 `CHANGELOG.md` 中记录，且记录必须写清楚两件事：**为什么改**（触发原因 / 要解决的问题）和**改了什么**（具体变更内容）。

- **为什么**：没有原因记录的变更不可追溯——日后回看只知道「改了」，不知道「当时为什么改、解决什么问题」，无法判断后续改动是否会破坏已有修复。
- **怎么记**：在当前版本的 CHANGELOG 条目下，按「新增 / 变更 / 移除」分类添加条目。每条必须包含：变更对象（哪个文件 / 功能）+ 原因 / 解决的问题。不要只写「修改了 X 文件」而不说明为什么。
- **记录不用问（2026-08-21 用户立）**：凡是有变更（增 / 删 / 改）都要记录到 CHANGELOG——**这是本分动作，直接记录，不需要先问用户「要不要记 CHANGELOG」**。用户明确说「记录 CHANGELOG 不用问」：每次改动完成后立即顺手记入，问「要不要记录」是多余的反 confirm。

### 溯源与防回归（核心要求）

**当新改动涉及 CHANGELOG 中已有记录的文件 / 功能 / 规则时，必须执行以下检查**：

1. **回溯历史条目**：先读 CHANGELOG 中该文件 / 功能的历史记录，理解当初是为了解决什么问题而做的改动。
2. **评估回归风险**：新改动是否会导致原来已解决的问题重新出现（回归）——具体来说，检查新改动是否：
   - 删除或弱化了当初为解决问题而加入的逻辑 / 规则 / 约束
   - 恢复了当初被移除的有问题的代码 / 配置 / 行为
   - 改变了当初为修复问题而设定的参数 / 条件 / 边界
3. **回归风险必须提醒用户**：如果评估后发现新改动**可能导致已解决的问题回归**，必须**立即、明确地告知用户**，说明：
   - 原来解决的是什么问题（引用 CHANGELOG 历史条目）
   - 新改动的哪个部分会破坏该修复
   - 如果不处理会有什么后果
   - 建议的处理方式（保留修复 / 做兼容调整 / 接受回归并记录原因）
4. **无回归则照常执行**：评估后确认新改动不影响已有修复，正常推进，无需额外提醒。

- **边界**：
  - **`CHANGELOG.md` 为项目标配**（2026-08-03 用户立：任何项目都必须有 `CHANGELOG.md` 与 `VERSION` 两个文件，缺失由 commit skill 第 9m 步自动新建）——本规则对任何项目都生效，不存在「没有 CHANGELOG 就不受约束」的情况。
  - 「查」操作（只读查看文件内容）如果**不产生文件变更**，不需要记录到 CHANGELOG——但如果是为后续改动做调研，建议在后续改动的条目中附带说明调研过程。
  - 盯盘过程中的高频信号记录写入 `signals/` 属运行时数据流，不逐条记入 CHANGELOG；但信号**机制**的变更（如新增 / 修改信号格式、响铃逻辑）必须记。

## 待办（TODO）管理：项目根 TODO.md 与 TODO-archive.md + 备忘录 MEMO.md（2026-08-01 立，2026-08-02 修订，2026-08-05 当日先改 todo-skill 制、随即撤销，定案为项目根文件制；2026-08-19 增补 MEMO.md 备忘录与「放弃」口径；2026-08-21 增补待办编号；2026-09-04 增补个人隐私类待办分流至 local 版文件）

凡「待办 / 下一步 / 代码现状（待办）」类内容——即**还没做、打算以后做**的事——一律写入**项目根目录**的两个文件：**`TODO.md`**（活跃待办，只放 `[ ]` 开头的未完成条目）+ **`TODO-archive.md`**（归档已完成 / 已更新条目）。**不设 todo skill、不依赖 skill 加载**：本节即是全部方法论（权威，对所有项目生效），数据文件放在项目根、不进 `.claude/skills/`。核心规矩：**TODO.md 只留未完成、已处理全部归档**，使「还有哪些没做」一眼全览、不被已处理条目淹没。**禁止写到其它任何地方**（含 skill 正文 SKILL.md、references、CHANGELOG、代码注释里的 `# TODO` 等）。

**TODO.md 的功能定位（2026-08-19 用户立）**：待办清单里的内容都是**要尽可能尽快处理**的，清单要**及时清空**——因此 **TODO.md 不设「长期备忘」这类无完成时点的分类**；比绿色紧急度还低的超低频需求（周期性 / 条件触发才需要做、无排期压力的备忘事项）一律放**项目根 `MEMO.md` 备忘录**（见下「备忘录 MEMO.md」小节），不进 TODO.md。

- **文件结构**：
  - `TODO.md`：**活跃待办**，只放 `[ ]` 开头的未完成条目；内部按**紧急度分节（`##` 二级标题，红色紧急度最紧急在前、橙色紧急度、黄色紧急度、绿色紧急度最不紧急在后，见下「优先级分类」）**，同一紧急度内可再按主题分节（`###` 三级标题，如「代码 / 机制」「交易规则 / 策略」）；节下条目按记录时间先后排列。
  - `TODO-archive.md`：**已处理归档**，`✅**已完成**` / `✅**已更新**` / `✅**已放弃**` 条目（保留归档时的紧急度标注，便于回溯「当初这条是什么级别」）；保留是为了日后回溯排查（当初打算做什么、做没做、什么时候做的、后来改没改主意），与 CHANGELOG 互补不重叠。
  - `MEMO.md`：**备忘录**（2026-08-19 立），超低频备忘条目（见下「备忘录 MEMO.md」小节）。
  - 这些文件都是项目文件，与 CHANGELOG.md 同等待遇、可被 git 跟踪。
  - **个人隐私类待办分流 local 版（2026-09-04 用户立）**：**个人隐私类内容不得写入公开版 `TODO.md` / `TODO-archive.md`**（它们会被 git 跟踪、随开源仓库公开），改写**项目根 local 版文件**——`TODO.local.md`（活跃待办）+ `TODO-archive.local.md`（归档），两文件须加入 `.gitignore`（与 CHANGELOG.local.md 的分流方式同理）。条目格式、紧急度分节、编号规则与公开版完全一致；**编号与公开版共用同一套编号空间**（取最大值时四个文件都要扫，见下「编号在项目内全局递增」）。公开版 TODO 头部加一行分流指引即可，指引措辞与条文本身**一律用中性表述（如「个人隐私类待办」）、不点明具体隐私类别——类别名本身即敏感信息**（公开仓库读者看到类别词即可推断仓库主的私人情况，2026-09-04 用户二次纠正：首版条文自己写了具体类别名，属同源泄露）。边界：local 分流针对「个人隐私类待办」；非隐私的普通技术待办照常写公开版，不因「有 local 文件存在」就把全部待办都塞进去。
- **优先级分类（2026-08-16 用户立；2026-08-17 用户改为四级紧急度；2026-08-17 用户再修订：命名弃「灯」用「色」，如「红色紧急度」，每次写入 TODO 必须判断）**：**每条待办写入 `TODO.md` 时必须判断严重度并标注类别，分四级，按紧急度从最紧急到最不紧急排列**——
  - **🔴 红色紧急度**：不修会直接亏钱、下错单、安全事故、数据/统计结论错误，或核心功能不可用——最紧急，须优先处理；
  - **🟠 橙色紧急度**：边界情况出错、防护缺口、口径不一致可能演化为实际损失——次紧急，排在红色紧急度之后计划处理；
  - **🟡 黄色紧急度**：文档措辞、格式漂移、卫生问题、不影响正确性的优化——较不紧急，有空再处理；
  - **🟢 绿色紧急度**：计划类新功能实现（新能力立项、改造方案落地，改期无实际损失）——最不紧急，按计划排期推进。
  - **怎么标（2026-08-17 用户修订：颜色只标标题、条目不标）**：颜色只出现在 `##` 分节标题上（「🔴 红色紧急度」「🟠 橙色紧急度」「🟡 黄色紧急度」「🟢 绿色紧急度」），**条目本身不再标注颜色 emoji**——避免标题与条目两处颜色不一致或混乱；条目紧急度由所在分节表达。判断拿不准往高靠（宁高勿低）。既有条目还带颜色 emoji 的，接触一条删一条（顺手清理，不必专门一次性返工）。既有分节标题还写「红灯 / 橙灯 / 黄灯 / 绿灯」的，接触一处改一处（顺手改为「红色紧急度」等，不必专门一次性返工）。
  - **为什么**：待办不分轻重混排，紧急的（会亏钱的 bug）和不要紧的（改个措辞）排在一起，容易先做了轻的、漏了重的；按严重度分层后「什么必须马上修」一眼可见，处理顺序有依据。
- **为什么**：待办散落在规范文档 / 代码注释里，会随文档迭代过期失真（规范描述的是「现在怎么做」，夹带「以后打算做」会让读者误判当前状态），且无法统一跟踪进度。集中到项目根两个文件一处，既是唯一任务清单、又不污染规范与变更记录；项目根是项目的通用位置、天然存在，不依赖 skill 加载机制，也省去维护 skill 及其各项目副本的负担。
- **怎么用**：
  - 想记一个待办 → 写到项目根 `TODO.md` 对应主题节（节不存在则新建），不要写进 SKILL.md / references / CHANGELOG / 代码注释。
  - **CHANGELOG 只记「已发生的变更」**（为什么改 + 改了什么），不记「待办」；没做完的事不进 CHANGELOG，做完后再记。
  - **SKILL.md / references 只写规范本身**（当前应怎么做），不夹带「代码现状（待办）」「计划以后迁移」等未决事项。
  - 代码里的 `# TODO` 也并入 `TODO.md`，代码注释改为陈述性说明（不留下「待办」语义）。
  - **每条待办必须附带记录时间戳（2026-08-01 用户补充，精确到分钟）**：格式「`（记录：YYYY-MM-DD HH:MM）`」；记的是**这条待办当前内容的写下 / 更新时间**（不是事件发生时间），事后改写正文要同步更新。时间戳用于判断哪条是最新意图，只精确到天就分不出先后。
  - **每条待办必须有唯一待办编号（2026-08-21 用户立；同日修订：编号加粗）**：格式「**T+序号**」——前缀 `T` 直接连序号、不带连字符（如 `T11`），且**编号整体加粗**（`**T11**`），写在 `[ ]` 之后、正文之前，如「`- [ ] **T11** 修复开盘价字段取错的问题（记录：…）`」。**每一条 `[ ]` 条目都必须有编号**（活跃、归档同此）。用户和 AI 沟通某条待办时直接用编号指代（「T11 处理了吗」「放弃 T7」），不必复述长正文——编号就是为了针对性沟通。
    - **编号在项目内全局递增、永不复用**：新条目编号 = 该项目 `TODO.md` 与 `TODO-archive.md` 中出现过的最大编号 + 1（写入前先扫这两个文件取最大值，两个文件都要扫——归档编号也算占用，防止新条目与历史归档撞号造成指代混乱；**项目若有 local 版 `TODO.local.md` / `TODO-archive.local.md`，取最大值时同样要扫**——local 与公开版共用同一套编号空间，2026-09-04 增补）。条目**归档后编号保留不动**，归档条目与新条目靠编号不复用天然区分。
    - **MEMO.md 备忘条目同样编号**，前缀用 `M`（同样连写加粗、如 `**M11**`）与待办的 `T` 区分；`MEMO-archive.md` 归档同样保留编号、永不复用，取最大值时 `MEMO.md` 与 `MEMO-archive.md` 都要扫。
    - **存量条目补编号（2026-08-21 存量规则）**：既有无编号条目，接触一条补一条（顺手补，不必专门一次性返工）——处理、改写、或与用户讨论到该条时，按上述取最大值规则补上编号；补编号属于编号登记、不改写正文内容，时间戳不必更新。
    - **为什么**：待办正文往往很长，沟通时复述正文既费字又容易对不上是哪条；给每条一个稳定编号后，「哪一条」由编号一锤定音，跨会话、跨 TODO / 归档两文件指代都无歧义。编号只用于指代，不表达优先级或顺序——优先级仍由紧急度分节表达，条目顺序仍按记录时间排。
  - **前后矛盾的待办以最新时间戳为准（2026-08-01 用户补充）**：同一件事先后记了两条意图相反的待办时，以时间戳最新的那条为准；旧条目打 `✅**已更新**` 进归档、不删，保留可追溯。
  - **做完改动要闭环（查 TODO.md → 归档标记 → 记 CHANGELOG）（2026-08-02 用户修订；2026-08-05 归档化）**：每次做完项目的任何改动后，查一下这项改动是否已在 `TODO.md` 里——若在，把该条目从 `TODO.md` **移入 `TODO-archive.md`**，按状态标记（「已完成」：`[ ]` 开头改成 `✅**已完成**` + `（完成：YYYY-MM-DD HH:MM）`；「已更新」：原条目内容一字不动、开头 `✅**已更新**` + `（更新：YYYY-MM-DD HH:MM）`，并在 `TODO.md` 另起一条新 `[ ]` 待办写最新决定）。「已完成」「已更新」加粗以一眼区分。移入归档后把已做出的改动（增 / 删 / 改）记到 `CHANGELOG.md`。**不要删除已处理条目**——归档保留是为了日后回溯排查（当初打算做什么、做没做、什么时候做的、后来改没改主意）；活跃待办只有 `TODO.md` 里 `[ ]` 开头的条目，`TODO-archive.md` 里的 `✅` 条目看到即跳过。
  - **用户说「放弃 / 不处理」= 移除待办 + 归档留痕（2026-08-19 用户立）**：用户对某条待办说「放弃、不处理」时，不是只从 TODO.md 删掉就完——该条目同样**移入 `TODO-archive.md` 归档**，状态标 `✅**已放弃**` + `（放弃：YYYY-MM-DD HH:MM）` + 放弃理由（用户裁定不做的原话要点），正文保留原条目内容（方法 / 前置结论等有用信息留在归档里可回溯）。「放弃」与「完成」的区别只在状态标记与理由，归档动作完全一致——**凡移出 TODO.md 的条目一律进归档、不裸删**。
- **备忘录 MEMO.md（2026-08-19 用户立）**：
  - **功能定位**：项目根 `MEMO.md`，专门放「不那么紧急、没有明确完成时点」的超低频备忘事项——优先级低于 TODO.md 四级紧急度中最低的绿色紧急度（典型：周期性任务如「每 3~6 个月轮换一次密钥」、条件触发任务如「样本 ≥30 笔后重新标定」）。TODO.md 是要尽快处理、及时清空的清单；备忘录是不设排期的低频记录。
  - **条目格式**：与 TODO.md 一致——`[ ]` 开头 + 唯一编号（`M` 前缀连写加粗、如 `**M11**`，见上「每条待办必须有唯一待办编号」）+ 记录时间戳（精确到分钟，`（记录：YYYY-MM-DD HH:MM）`）；周期性 / 条件触发类条目建议写明**下次触发的时间锚点或条件**（如「下次不早于 2026-11-17」「样本 ≥30 笔后」），翻到即可判断要不要动。
  - **完成与归档**：备忘条目做完后移入**专属归档文件 `MEMO-archive.md`**（项目根，与 `TODO-archive.md` 平行、互不混放——待办的归档进 TODO-archive、备忘的归档进 MEMO-archive，回溯时各自成体系），状态标 `✅**已完成**` / `✅**已更新**` / `✅**已放弃**` + 对应时间与理由，格式同 TODO-archive；或条件未满足时在本文件内更新状态 / 计数（如样本计数刷新）。
  - **触发时机**：不设自动提醒——相关场景出现时（复盘发现样本够了、周期到了、怀疑泄漏等）由用户或 AI 主动翻本文件对照。AI 在相关场景（如复盘产样本数、到期日临近）应想起翻 MEMO.md。
  - **新建项目**：不强制预建 MEMO.md（多数项目没有备忘类内容）；第一次有备忘需求时创建即可，头部写功能定位说明（参考 DayTradingAgent 的 MEMO.md）。
- **边界**：本条管的是「待办 / 未决 / 计划以后做」这类内容；已完成变更的记录（CHANGELOG）、当前规范的描述（SKILL.md）、陈述性说明（代码注释描述这段代码是什么）不受限。敏感信息（账户号、API key、token 等）同样禁止写入 TODO 文件——它们会被 git 跟踪进仓库，一律用占位符 + 「真实值见本机配置」表述（见「敏感信息禁止写入未被 .gitignore 忽略的文件」节）；**个人隐私类待办按上文「个人隐私类待办分流 local 版」整体分流到 local 文件**——这类内容没有占位符可填，与财务状况类敏感信息同理，唯一正确姿势是不写进公开版（条文与指引本身也不点明类别）。

## 通用能力开源单一出口（2026-08-09 用户立，取代「skill 项目副本的存在原因」）

**新建 Agent 项目一律不放与全局通用能力重复的内容**——`~/.claude/skills/`、`~/.claude/rules/` 里的通用 skill / rules（如 anysearch、find-skill、通用三件套），不再复制进各 agent 项目的 `.claude/`。通用能力的开源分发统一经 **CapabilityManagerAgent（Prometheus）的 `claude/` 镜像**（`skills/`、`rules/`、`CLAUDE.md` 三部分，见「底层通用能力开源」节）一次性完成——clone 该项目即得全部通用能力；各 agent 项目只放自己独有的内容（2026-09-03 用户修订：新建项目一律不建 `.claude/` 目录，见「新建 Agent 项目的脚手架与开源约定」节）。

- **为什么**：全局 `~/.claude/` 是运行时实际加载的「活」源头；每个项目放一份副本意味着通用能力一改动就要同步到所有项目，副本容易过期分叉（2026-08-09 新建 NetOpsAgent 时即发现 anysearch `runtime.conf` 副本与全局不一致、find-skill 副本多出 `.env.example`）。统一单一出口后，全局改一处、镜像同步一处，各项目零维护。
- **怎么用**：新建 Agent 项目时**不再建 `.claude/` 目录**（2026-09-03 用户修订，见「新建 Agent 项目的脚手架与开源约定」节：`CLAUDE.md` 直接放项目根 + 项目根 `AGENTS.md` 软链接指向它）；需要通用能力时从全局 `~/.claude/` 或 CapabilityManagerAgent 获取，项目内不留任何副本。
- **边界**：本规则管「新建项目」；**已存在副本的既有项目**不做强制回退清理——其副本仍按下方 anysearch / find-skill 同步小节维护（保持一致即可），是否清理由用户另行决定。

## 写 skill 内容须依据 skill-creator（2026-07-31 用户立）

凡是**新建 skill、或修改已有 skill 的内容**（SKILL.md 正文、description、references、scripts 组织等），必须**先读 skill-creator skill**（`~/.claude/skills/skill-creator/`），按它的方法论来写，不能凭感觉自由发挥。

- **为什么**：skill-creator 是专门用来创建 / 改进 skill 的方法论工具，沉淀了经过验证的写法——最核心的是 Progressive Disclosure（渐进式披露）：元数据（name + description）始终在上下文、SKILL.md 正文在触发时加载（理想 <500 行）、scripts / references / assets 按需加载；description 要写得"pushy"（明确列出触发场景、避免欠触发）；详情要拆进 references 并在主文件留清晰指针。不按这套来，写出的 skill 容易臃肿（主文件超长、详情全堆正文）、触发不准（description 太弱导致该触发时不触发）、难维护。DayTradingAgent 的 trade skill 就曾因违反 Progressive Disclosure（主文件 543 行、规则全堆正文）被按 skill-creator 重写过。
- **怎么用**：
  - 新建 skill：走 skill-creator 的完整流程（Capture Intent → Interview → Write SKILL.md → 写测试用例 → 跑 eval → 迭代），至少在结构上遵循它的 Anatomy + Progressive Disclosure + Writing Patterns。
  - 修改 / 优化已有 skill 内容：先读 skill-creator 的 Skill Writing Guide，确保改动符合其结构要求（主文件精简、description pushy、详情拆 references）；大改后可用 skill-creator 的 eval 流程验证触发与效果。
  - description 优化（提升触发准确率）：用 skill-creator 的 skill description improver 脚本。
- **边界**：
  - 本条管的是 skill **内容怎么写**（结构 / 方法论），不管 skill 的存放位置 / 副本同步（那是「skill 项目副本的存在原因」和各 skill 同步小节的事）。
  - 只改 skill 里的一两个错别字 / 小措辞，不必每次都重走 skill-creator 全流程；但涉及结构调整、新增章节、重写 description 等"内容性改动"时，必须以 skill-creator 为准。
  - skill-creator 自身在 `~/.claude/skills/skill-creator/`（全局可用），无需额外安装。

## Skill 内容纯净性：核心可开源 + 私人信息用户级存放（2026-09-06 用户立）

**所有 skill 的核心功能文件（SKILL.md / references / scripts / README / description）必须保持可开源标准：不含对 clone 者来说莫名其妙或无用的内容；本机私人信息一律像凭证一样存放在 skill 目录下被忽略的本机数据子目录中**（如 backup skill 的 `endpoints/`——gitignore + 不进 CapabilityManagerAgent 开源镜像），不进功能文件。以后创建 skill 都要遵守，维护既有 skill 同样适用。

- **为什么**：skill 是可复用、可分发的能力单元，价值在通用性——clone 者拿到就应该能用。私人信息混进功能文件既是泄露风险（随镜像公开），也让 clone 者困惑（「用户 X 日立」是谁？这个 token 指向谁的云盘？）。凭证纪律已经验证了这个模式：凭证本体放工具自管位置或被忽略的本机目录，功能文件只记「位置与用法」——把同样的模式推广到全部私人信息。
- **私人信息包括**：token / folder 标识、个人云盘结构与命名、本机环境细节（代理配置、端口等）、带「用户 X 日立」署名的个人规则出处、个人事件叙述、指向特定个人的配置值。
- **怎么用**：
  - 私人信息 → 存 skill 的本机数据子目录（注册表字段或独立文件，与凭证同模式）；功能文件用占位符表达机器差异（如 `<folder-token>`）；
  - 个人配置值（白名单、模式、路径等）→ 放注册表 / 配置文件，功能文件只描述机制并指向配置（「当前值见注册表」）；
  - 通用坑与通用流程（对 clone 者有价值的，如 CLI 的路径限制、报错语义）→ 保留在功能文件；
  - 个人规则的来龙去脉与事件教训 → 记 CapabilityManagerAgent 的 CHANGELOG（公开、写中性摘要）或本机文档，不进 skill 正文；
  - 新建 skill 时按此设计；既有 skill 接触到时顺手清理，不必专门一次性返工。
- **边界**：本条管 skill 功能文件的内容纯净性；全局 / 项目级规则文件（CLAUDE.md、rules、AGENTS.md）记录个人规则不受限——那些本就是用户自己的规则文件，不是对外分发的能力单元。

## rules 文件必须在 CLAUDE.md 中 @ 引用（加载机制纪律，2026-07-20 立）

`@` 引用是 rules 文件进入上下文的**唯一途径**——只有被 CLAUDE.md `@` 引用的 rules 文件，才会随 CLAUDE.md 自动加载进上下文（S 级、每次会话无条件在场、优先级最高）；**未被引用的 rules 文件不会自动加载，等于白写**。这是 rules/ 机制区别于 SKILL.md / MEMORY.md（按固定文件名被系统主动加载）的固有约束。

- **项目级**：`.claude/rules/` 下每一个规则文件，都必须在项目级 `.claude/CLAUDE.md` 里 `@` 引用（写明 `@路径` + 一句话摘要）。
- **全局级**：`~/.claude/rules/` 下每一个规则文件，都必须在全局 `~/.claude/CLAUDE.md` 里 `@` 引用。

**怎么用**：
- **新增 rule 文件** → 同步在对应 CLAUDE.md 加一行 `@` 引用。
- **删除 rule 文件** → 同步去掉对应 CLAUDE.md 里的 `@` 引用。
- **定期核对** rules/ 目录与 CLAUDE.md 的 `@` 清单一致——目录里有但 CLAUDE.md 没引用 = 漏加载（白写）；CLAUDE.md 引用了但目录里没文件 = dangling 引用。两者都要及时修。

**为什么**：rules/ 没有「按固定文件名自动加载」的机制（不像 SKILL.md / MEMORY.md 那样系统会主动按文件名找），它的文件被加载的唯一途径是被某个 CLAUDE.md `@` 引用。漏了 `@`，该规则在会话中完全不在场、起不到约束作用——**文件存在 ≠ 被加载**。

## 中英双语 README 内容自动同步（2026-08-17 用户立）

凡项目同时存在中英双版 README（常见形态：英文 `README.md` + 中文 `README_cn.md`，以项目实际双版文件名为准），**两版内容必须时刻保持同步**：每次改动其中任何一版的**内容**（措辞、信息、列举项、口径、数字、结构），都必须在**同一轮改动里自动同步另一版**，**不需要问用户「要不要同步」**。

- **中文版为权威方向**：用户用中文打磨措辞，英文版跟随同步；用户直接改英文版的情况同理反向同步中文版。
- **为什么**：双语 README 是同一内容的两种语言表达，只改一版会让两版信息不一致，读者看到过期或矛盾的另一半；每次询问「要不要同步」是多余的反 confirm——同步是内容改动的固有部分，不是可选步骤。（2026-08-17 xhqing 赞助段改措辞后只改了中文版、还停下来问用户英文版要不要同步，被用户纠正后立此规。）
- **怎么用**：
  - 改中文版某句 → 同一轮顺带改英文版对应句；改英文版 → 同步中文版。
  - 英文按英文习惯表达，**不必逐字直译**，但**语义内容必须对齐**——信息点、列举项、口径、数字一处不能少、不能多、不能变。
  - 语言固有差异允许：语序、地道表达按各自语言规范来（如中文「如……等」的非穷尽语义，英文 "such as" 一词已含，不必再叠 "etc."）。
- **边界**：本条管「内容」同步；两版**语言特有**的内容（如各自的语言切换链接——英文版跳中文版的链接文字统一为「简体中文」）不算内容差异，不受影响。仓库只有单语 README 的，本条不适用。

## 底层通用能力开源：全局权威 ↔ 本项目镜像，三部分时刻一致（2026-07-31 立；2026-08-04 反转权威方向 + 范围收为三部分）

本项目（CapabilityManagerAgent）是把 Claude Code 智能体的**底层通用能力底座开源出去**的源头仓库。**全局 `~/.claude/` 是通用能力的权威源**；本项目 `claude/` 下对应的 3 部分——`skills/`、`rules/`、`CLAUDE.md`——是全局权威源的**开源镜像**，必须与全局**时刻保持逐字节一致**。

- **目录布局**：本项目 `claude/` 目录（不带点）是全局 `~/.claude/` 的开源镜像。因目录名不是 `.claude`，Claude Code 不会自动加载它、本项目运行时也不依赖它（本项目运行时的能力由全局 `~/.claude/` 直接提供）；`.claude/` 目录保留为本项目**独有的项目级能力目录**，放本项目特有、不随通用能力同步的内容（如 capability-manager skill——Prometheus 本项目的专属工具）。两者分工：`claude/` 镜像「开源给全世界的通用能力」、`.claude/` 放「本项目自己的项目级能力」。
- **权威方向（2026-08-04 反转）**：**全局 `~/.claude/` 是唯一权威源**，本项目 `claude/` 对应部分是它的镜像。改动先在全局落地（全局是所有项目运行时实际加载的「活」源头），再同步覆盖到本项目 `claude/` 镜像；反过来不准只改 `claude/` 镜像而不动全局（那样镜像会与权威源分叉）。**为什么以全局为权威**：全局是实际运行时加载的中心、是「活」的；`claude/` 只是把全局内容开源出去的快照，以全局为权威更贴合实际使用，也避免了「权威源不被加载、要靠镜像回流」的别扭。
- **范围（2026-08-04 收为三部分）**：`skills/` 下所有**通用** skill、`rules/` 下所有规则、根 `CLAUDE.md`——这三部分在全局 `~/.claude/` 是权威、在本项目 `claude/` 是镜像，逐字节相同。**不含 `commands/`**（2026-08-04 起从同步体系去掉，各处 commands 自行管理）；**不含项目级专属 skill**（如 capability-manager，放 `.claude/`、不进通用同步）。
- **唯一例外：敏感信息**。涉及密钥、凭证、本机运行数据的内容（如 `find-skill/.env` 里的 SkillsMP 密钥、`find-skill/cache/` 里的本机数据、`settings.local.json`），不在「逐字节一致」的硬要求内——由本项目用 `.gitignore` 在项目级隔离，确保敏感信息不随开源仓库泄露。除此之外**不存在任何特例**：包括 `runtime.conf` 路径也不再特殊对待，项目副本与全局逐字节相同，clone 者拿到后按本机路径自行适配即可。
- **为什么**：把全局钉成权威源（实际运行时的中心），`claude/` 作为开源镜像，任何人 clone 本项目即得通用能力快照；全局改一处、镜像同步一处，避免两边分叉、互相漂移。
- **怎么验证**：每次改动后用 `diff -r ~/.claude/<部分> claude/<部分>` 核对三部分（`skills` / `rules` / `CLAUDE.md`）是否仍逐字节一致（被 `.gitignore` 隔离的敏感文件不参与公开比对，是唯一允许的差异）。
- **与下方各 skill 同步小节的关系**：本规定管的是「全局 ↔ CapabilityManagerAgent `claude/` 镜像」这一层（全局为权威）；下方 anysearch / find-skill 同步小节管的是「全局 ↔ 各 agent 项目副本」那一层（同为全局权威，向各 agent 分发）。两层方向一致——全局为唯一权威，本项目 `claude/` 镜像与各 agent 项目 `.claude/` 副本都从全局来，互不冲突。
- **自动同步、无需每次询问（2026-08-01 用户立；2026-08-04 方向反转）**：一旦发现全局 `~/.claude/` 与本项目 `claude/` 镜像之间出现分叉（无论哪边领先），**直接自动同步对齐，不要再向用户询问「要不要同步」**。同步方向以全局权威优先——理想流程是改动先落全局、再镜像 `claude/`；若分叉是 `claude/` 镜像领先（比如临时直接改了镜像），就把 `claude/` 内容覆盖回全局、一次性对齐后，继续走全局优先。
- **同步动作只记本项目的 CHANGELOG（2026-08-01 用户立）**：通用能力同步这件事本身的变更记录，**只记在本项目（CapabilityManagerAgent）的 `CHANGELOG.md`**，**不记到其它任何项目的 CHANGELOG**（如各业务项目 DayTradingAgent 等）。为什么：底层通用能力的同步归这个开源仓库管、是它本身的事，不该混进各业务项目自己的变更记录里、污染那些项目的 changelog。

## 规矩必须配套工具强制（2026-08-30 用户立，元规则）

**任何规矩指定后，都要尽可能通过工具强制辅助防止忘记——用代码 / hook / settings deny 等硬约束落地，仅仅靠文本记录在 rules / skills 或 CLAUDE.md 里是不够的。**

- **为什么**：2026-08-30「连接远程禁止复用窗口」的规矩刚立了几分钟，Agent 转头又用 `open vscode://` URI 复用了用户窗口——文本规则在长会话、多任务切换中必然被遗忘。只有工具层拦截（hook 直接 deny 违规命令）才是可靠防线，文本只是解释「为什么」的补充。
- **怎么用**：新立规矩时的标准动作——① 先判断该规矩能否映射为可检测的命令 / 操作模式（如「杀 X 前先问」→ 拦截对 X 的 kill 类命令；「禁止某种触发方式」→ 拦截该方式对应的命令特征）；② 能映射的就写进 `~/.claude/hooks/pre-tool-use-guard.sh`（PreToolUse 钩子，返回 deny 即拦截）或 settings.json 的 `permissions.deny`；③ 不能映射的（如「输出风格」类）才只靠文本。
- **现有硬约束**：`~/.claude/settings.json` 的 `permissions.deny`（EnterPlanMode、git push --force 等）+ `~/.claude/hooks/pre-tool-use-guard.sh`（杀 VSCode 进程须授权标记、禁 `open vscode://vscode-remote` URI 复用窗口）。改规矩时要同步改对应的强制工具，两边不能脱节。
- **边界**：本条是元规则，管「规矩怎么落地」；工具强制是下限防线（防遗忘），不取代文本规则的说理与边界描述——两者并存，工具拦「红线」，文本管「判断」。

## 连接远程 VSCode Server 禁止复用当前窗口（2026-08-30 用户立；工具强制已配套）

**凡是触发 VSCode Remote-SSH / Remote Tunnel 等远程连接（连接远程 VSCode Server）的操作，禁止复用用户当前正在使用的 VSCode 窗口——必须强制在新窗口中打开。**

- **为什么**：2026-08-30 用 `open "vscode://vscode-remote/ssh-remote+win-ai/..."` URI 触发远程连接时，VSCode 复用了用户当时正在另一个项目里工作的窗口，用户的工作现场（当前项目、编辑中的文件）被远程会话顶替，体验像「工作目录被改了」，造成困扰。远程开发会话应与用户本地工作窗口严格隔离。
- **怎么用**：触发远程连接时一律加「新窗口」语义——命令行用 `code --folder-uri "vscode-remote://ssh-remote+<host>/<远端路径>" --new-window`；URI 方式（`vscode://vscode-remote/...`）会复用现有窗口，**不要用**；若必须经 GUI 操作（Command Palette），选「Connect to Host… in New Window」类命令。
- **工具强制**：`~/.claude/hooks/pre-tool-use-guard.sh` 已硬拦截 `open vscode://vscode-remote` 形态的命令（直接 deny）——即使忘记本条，钩子也会拦下。
- **边界**：本条管「AI 触发的远程连接」如何开窗口；用户自己在 VSCode 里手动连接不受限。本地项目窗口之间的切换、打开本地文件夹不受本条约束。

## 杀 VSC 进程前必须先问（2026-08-30 用户立；工具强制已配套）

**凡是杀 VSCode（VSC）进程的操作——`pkill`、`kill`、`killall`、`osascript quit` 后强制结束等一切会让 VSCode 退出 / 重启的手段——必须先用 AskUserQuestion 向用户说明要杀什么、为什么，等用户授权后再执行。**

- **为什么**：VSCode 可能挂着用户未保存的窗口状态、正在跑的任务、调试会话；擅自杀进程会造成用户工作现场丢失。用户要求把杀进程的决定权留在自己手里（2026-08-30，Agent 准备杀 VSC 进程前未先问被用户纠正）。
- **怎么用**：执行任何杀 VSCode 进程的命令前，先 AskUserQuestion（列出将杀的进程范围 + 原因），用户同意才动手；不同意就不杀、改用别的方案（如让用户手动重启）。**工具强制**：`~/.claude/hooks/pre-tool-use-guard.sh` 已硬拦截未带 `# AI_AUTHORIZED_KILL_VSC` 标记的杀 VSCode 命令——获得用户授权后，在命令里加该注释标记即可放行执行。
- **边界**：本条只管「杀进程」这类强制手段；查询类操作（`ps`、查看进程状态）不受限。杀其它应用的进程不属本条，但同样建议遵循「不可逆操作先确认」的一般原则。
