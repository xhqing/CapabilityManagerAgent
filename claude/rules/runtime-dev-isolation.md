# 运行版本与开发版本隔离规范（禁止 npm link / 本地直跑开发源码）

## 核心原则

**任何项目的「实际在用的运行版本」与「开发中的版本」必须严格隔离，不能混为一谈。**

- **开发中的代码必须走完整发布流程（打 tag + GitHub Release）之后才可以在实际环境中使用**。
- **实际使用的版本必须从 GitHub Release 重新安装或更新**（下载 Release 产物全局安装 / 覆盖安装），**不是**从开发目录链接、也不是从开发目录直接运行。
- **禁止用 `npm link`（或 pip editable install、`cargo install --path`、软链接等一切等价手段）把开发目录链接为全局命令**；同样禁止让常驻服务（daemon / 后台进程）直接运行开发目录里的源码文件。

**为什么**：开发目录的文件随开发随时变化。一旦全局命令或常驻进程指向开发源码，运行版本就完全不可控——开发中的半成品改动会实时污染实际环境，出问题时无法区分「是发布的版本有 bug」还是「本地未完成的改动引入的 bug」，排查与回滚都失去基准。2026-08-30 在 CC-Bridge 实际踩坑：为验证修复把项目 `npm link` 成全局命令，glm daemon 随之跑在开发源码上，线上行为直接依赖未发布的开发文件。

## 怎么用

1. **开发期验证**：在开发目录内自测（本地起服务、跑测试），用完即停，**不把开发目录挂为全局命令、不让常驻 daemon 指向它**。临时验证若确实需要起 daemon，验证结束后立即解除并恢复正式安装。
2. **要正式使用某个版本**：走该项目的发布流程（commit → 打 tag → GitHub Release），然后**从 Release 产物重新安装**（如 `npm install -g <Release 下载的 tgz>`），再重启服务使其从安装副本运行。
3. **自检**：`npm list -g <pkg>` 出现 `-> .../Projects/...` 箭头即为违规的 link 状态，必须立即按发布 + 重装流程纠正；`ps` 查看常驻进程的脚本路径，指向开发目录即为违规。
4. **代价须知**：某修复尚未发版时，正式环境就是用不上它——这是隔离的固有代价，**不构成跳过发布流程的理由**。正确做法是尽快走发布流程，而不是用 link 通融。

## 边界

- 本规则适用于**任何项目**，不限于某个具体项目（CC-Bridge 的事故只是起因，规则面向所有项目）。
- 各项目若有更具体的安装 / 升级细则（如 CC-Bridge 的 `.claude/rules/cc-bridge-install.md`），以项目细则为具体操作指引，本规则为总纲；两者冲突时以更严格者为准。
- 开发目录内部的自测运行（不起全局命令、不做常驻服务指向）不受限。
