# add — git add 前的敏感信息预检分流

## 定位：解决什么问题

在文件进入暂存区**之前**把敏感信息拦住。两层扫描引擎分工：

- **gitleaks（工具层，确定性）**：已知格式的密钥（API key、token、私钥约 200 种）+ 自定义规则（公网 IPv4 字面量、服务商标识词表等，配置在本机 `~/.gitleaks.toml`）。规则命中即拦，不受 AI 注意力影响。
- **AI 语义扫描（语义层）**：无固定格式的敏感内容——财务状况（收入目标、本金、资产、负债、财务紧迫性、投入状态）、个人隐私标识（账户号、证件、真实联系方式、连接串实值）、敏感叙述（身份 + 网络出口 + 绕行手段的故事线、合规拒单报文引用、服务商节点代号）。这类内容任何正则都抓不到，只能靠语义判断。

分流结果：**干净文件自动进暂存区，可疑文件留在工作区等人工过目**——用户肉眼过目的量从「全部改动」缩到「机器拿不准的少数」。

## 授权边界（硬性，不可越过）

1. **用户触发 `/add`（或当轮明确要求 add）= 授权当次对预检通过的文件执行 `git add`**。这是全局 CLAUDE.md「Git 暂存区禁止 AI 自主增删改」条款的授权例外（2026-09-22 立）。
2. **只增不改**：本 skill 绝不触碰暂存区已有内容——不执行 `git restore --staged`、`git rm --cached`、`git reset`、`git mv` 等任何会改动暂存区现有内容的命令。发现暂存区里已有可疑内容时只报告，不动它（留给用户处理）。
3. **不 commit、不 push**：那是 commit skill 的职责。
4. 用户口头确认「这几个没问题，add 吧」= 当轮授权 add 这几个文件；确认后文件若有新改动，须重新扫描再 add。

## 执行流程

### 第 0 步：确定候选集

- 用户指定了文件 / 目录 → 只处理指定的。
- 未指定 → 处理工作区全部未提交改动：`git status --porcelain`。
- `.gitignore` 已忽略的文件不进候选。
- **删除类改动（D 状态）**：直接 add（删除动作本身无敏感内容可泄）。
- **重命名（R）与修改（M）、新增（??/A）**：进入扫描。

### 第 1 步：不入库检测（先于敏感扫描，便宜先做）

候选中出现以下任一情况 → 不 add，归入「🚫 不建议入库」并附 `.gitignore` 建议（与 commit skill 的 cache 检测口径一致，把拦截提前到 add 阶段）：

- 名字含 cache 的文件 / 目录（`__pycache__/`、`.cache/`、`*.cache`、`cache/`）；
- 二进制文件、本地数据库文件（`.db`、`.sqlite`）；
- 超大文件（> 5MB，先问用户是否真要入库）。

### 第 2 步：工具层扫描（gitleaks）

```bash
gitleaks dir <候选文件所在目录或文件清单> --config ~/.gitleaks.toml --no-banner -v
```

- 对候选文件逐个跑（或对所在目录跑后按文件清单过滤结果）。
- 命中输出含 File / Line / RuleID / Finding——**命中文件一律进人工清单，附 RuleID 与行号**。
- **gitleaks 未安装或执行失败** → 降级为 AI 正则扫描（私钥头 `-----BEGIN`、token 特征串、公网 IPv4 正则等），并在报告开头标注「⚠️ 工具层未生效，本次仅 AI 扫描，强度降级」。

### 第 3 步：AI 语义扫描（以内容 change block 为判断单位）

对候选中的文本文件**逐个读内容**（不是抽样），以**内容 change block** 为最小判断单位——修改类（M/R）看 diff 的 hunk，新增类（??/A）整个文件都是新内容、按逻辑段落或配置项分块——逐块判断三类无格式敏感内容：

1. **财务状况**：收入目标与实际收入、本金、资产、负债、存款、财务紧迫程度、职业投入状态等描述；
2. **个人隐私标识**：券商 / 银行账户号、证件号、真实姓名 + 联系方式、真实 IP / SSH 连接串、密钥实值;
3. **敏感叙述**：把「身份 + 网络出口地域 + 绕行手段」串成故事线的叙述、合规拒单报文原文引用、服务商节点代号系列。

判断纪律：**拿不准的块就按可疑处理**——宁可多留一个块给人工看，不可放过一个。这类内容一旦进公开仓库就是永久明文。

### 第 4 步：过目与否以内容块为单位，文件类型不触发人工（2026-09-22 用户定）

**是否需要人工过目，判断依据是具体内容块有没有疑似敏感信息，不是文件 / 文档的类型**：

- 新增文档类（`*.md` 新文件、`docs/` 下新文件）、配置类（`*.json` / `*.yaml` / `*.toml` / `*.env*`）、记录类（`*.log`、笔记、导出数据）文件，扫描之后所有内容块都没有敏感信息 → **直接进暂存区**，不需要人工过目——「它是新增文档」这个类型本身不构成过目理由。
- 触发人工过目的唯一理由是**具体内容块疑似敏感**：语义扫描拿不准的块、gitleaks 命中的行。报告理由必须精确到块（行号 + 内容片段），让用户看的是「这一块为什么可疑」，不是「这个文件是什么类型」。
- 这些类型仍是敏感叙述高发区，第 3 步对它们逐块扫描时要格外仔细（宁可慢），但把关强度落在扫描质量上，不再落在类型一刀切的强制人工上——「扫得细」取代「必须过目」。

### 第 5 步：分流执行

- **干净文件**（工具 + 语义双通过，所有内容块均无敏感信息）→ 一条命令批量 add：
  `git add -- <文件清单>`
- **含可疑内容块的文件** → 留在工作区，等用户过目。

### 第 6 步：输出报告（三段式）

```
✅ 已加入暂存区（N 个文件）
   - 文件1、文件2、…

👁 需人工过目（M 个文件，已留在工作区）
   - 文件A —— 理由：gitleaks 命中 [rule-id] 第 X 行：<片段>
   - 文件B —— 理由：第 X-Y 行内容块语义疑似财务状况描述：<片段>

🚫 不建议入库（K 个，附 .gitignore 建议）
   - 文件D —— cache 目录
```

报告末尾给一句指引：过目没问题 → 回复「没问题，add」即可；有问题 → 改完文件再说「重新预检」。

## 降级与异常

- gitleaks 缺失：见第 2 步降级逻辑（同时提示 `brew install gitleaks`）；
- 候选为空：直接报告「工作区无待处理改动」；
- 用户确认 add 时文件又被改过：重扫该文件后再 add（防止确认与执行之间的窗口期写入敏感内容）。

## 与其他 skill 的衔接

- **commit skill**：`/add` 管工作区 → 暂存区；`/commit` 管暂存区 → 仓库 → 远程。commit skill 的暂存区敏感扫描原样保留（最后防线，纵深防御），其暂存区来源现在有两种：经 `/add` 预检加入、用户手动 add。
- **gitleaks pre-commit hook**（全局 hooks 目录）：commit 时对暂存区再扫一道，是本 skill 之后的又一道工具防线。
