# 预发布试用与发版验收

本文件是 dev-workflow 第 9 / 10 步的完整规矩。位置：**合并进 main 之后（CI 已独裁合并）、正式发版之前**——用户以实际使用预发布版本的形式验收，试用满意才正式发版（2026-09-21 用户定：人工验收是过程，不是合并前的瞬时门禁）。

## 为什么验收放在试用、把关放在发版

- **机器门禁管客观回归（合并），人工验收管主观满意（发版）**：CI 全量测试能断言「改 A 没坏 B」，断言不了「好用」「是用户想要的样子」——用例是需求的机器翻译，翻译有漏（界面、体验、文案难以用例化）。主观维度不放在合并环节（等人工会卡住集成节奏），放在发版环节把关。
- **验收需要时间，过程化才真实**：真实使用（小时到天级）才能暴露手感、稳定性、边角场景的问题——「立刻验收完」反而验收不出这些。预发布试用把验收变成使用过程，发现的问题走修复循环消化在发版前。
- **CI 慢的窗口期正好开始试用**：复杂项目 CI 可能跑很久，等 CI 的窗口与试用的时间天然重叠——PR 建好、CI 开跑时就可以发 rc.1 让用户装上，CI 绿合并时试用已在进行中。
- **合并进 main ≠ 发布**：main 是集成分支（CI 保证每步绿），发布是独立的门。试用期间 main 持续前进正常，用户验收的是「试用中的预发布版本 + 持续演进的现实」，不是某个冻结时点；满意了，正式版发的就是那时的 main 快照。

## 预发布（验收主通道）

- **形式**：`v<目标版本>-rc.N` / `-beta.N` 的 prerelease tag + `--prerelease` 标记的 GitHub Release，产物从对应分支 / main 构建，用户从 Release 页安装——走真实发布链路验收（把发布环节的风险也前置暴露），兼供早期尝鲜。供料两条通道：
  - **自动预发布（配了 auto-rc workflow 的项目，主通道）**：`.github/workflows/auto-rc.yml`（模板见 `assets/auto-rc.yml`，两个定制点：workflow 名与 ci.yml 一致、构建命令按项目改）监听 main 的 CI workflow，全绿后自动推导下一个 rc tag——目标版本 = CHANGELOG 顶部第一条未发布的语义版本，没有则 VERSION 的 patch + 1；rc 号 = 同目标版本下已有 rc.* 最大值 +1——然后构建产物、打 tag、发 `--prerelease` Release（notes 自动列自上个正式 tag 以来的提交）。时序：PR 的 CI 绿 → auto-merge 合并 → main 的 push CI 再跑全量 → 绿 → auto-rc 发新 rc，即 rc 比「合并完成」再晚一个 CI 周期；只对应「CI 测过的 main 状态」（main 的 CI 红不发；concurrency 排队期间 main 前进则旧运行跳过、由新运行发）。验收与修复循环都围绕这个自动供给：用户随合并装最新 rc、问题修复合并后 rc.N+1 自动出现，全程无需手动发版动作。
  - **手动预发布（未配 auto-rc，或合并前提前试用）**：从功能分支（合并前）或 main（合并后、带修复）打 prerelease tag，产物从对应分支构建；操作规范（版本号推导、流程差异、必带 `--prerelease`）见 release skill 预发布通道。CI 慢的窗口期等不及 auto-rc（它只在合并后触发）时，从功能分支手动发 rc.1 提前开始试用；项目配了 auto-rc 且用户要 rc 时，先报告最近的自动 rc（可能已够用），避免重复手发。
- **不 bump 版本文件**：VERSION / package.json / CHANGELOG 都不动（正式发版时经 `/bump` 统一改）——预发布只存在于 tag 与 Release 层面，与「功能分支不碰版本号」纪律一致。auto-rc 的版本号推导同样只在 tag 层面计算，不写任何文件。
- **迭代递增**：试用发现的问题修复合并后，递增预发布号再发（rc.1 → rc.2 → …，auto-rc 自动、手动通道手动），用户每次拉新版继续试用；旧预发布 Release 保留不动（正式版发布后自然被取代）。
- **验收通过的表现 = 用户决定正式发版**（`/bump` + `/release`）——没有单独的「验收报告」仪式，发版决定本身就是验收结论。

## 本地测试包（轻量选项）

快速冒烟（构建验证 + 即时装、小改动不值得发 Release 的场景）用本地构建的测试包：

1. 在 dev 的 worktree 里按项目发布工艺构建（vsce package、npm pack 等，按项目来）；
2. 版本标识区别于正式版（如临时加 `0.0.0-test`），构建完把源码里的临时版本号**还原干净**——不占正式版本号；走预发布通道时无需临时版本号（tag 后缀即标识）；
3. 产物放 worktree 的 `tmp/`（遵守 tmp-dir-for-artifacts 规则），worktree 删除时一起清；
4. 不打 tag、不发 GitHub Release——只服务本次冒烟，不进发版流水线；与运行版隔离规则不冲突（一次性验收安装，验收完被卸载或被正式版覆盖）。

完整验收（主观满意把关）以预发布试用为主，本地测试包只做快速冒烟。

## 试用反馈的处置

- **实现不符合需求 / 体验不满意**（功能没做完、行为和 Issue 预期不一致、手感不好）→ 修复循环：开新 Issue（或复用原 Issue 评论跟进）→ 测试 Agent 先写失败测试（复现新问题，先红，开发不碰测试）→ fix 分支实现到绿 → push + 建 PR + enable auto-merge（CI 绿合并）→ 递增预发布号（rc.N+1）→ 用户再试用。循环到满意为止，正式发版随之推迟。
- **需求本身要变**（用户用完想改主意）→ 更新 Issue（编辑 / 评论写清新需求与新验收标准）→ 测试 Agent 按新 Issue 重出 / 改测试（出题上下文不见过实现——测试 Agent 的会话天然满足；开发不碰测试，hook 强制）→ 迭代走新一轮分支循环。需求变更不经这条通道、开发 Agent 自己揣摩着改，会做成「没人定义过的需求」。

## main 与发布的语义闭环

走完本流程后：**main = 远端 CI 全量测试通过的集合**（机器门禁独裁合并，杂事与功能一律）；**正式发布的版本 = 用户使用验收过的 main 快照**（试用满意才 `/bump` + `/release`，人工门禁落点在发版）；**预发布是两者的桥**——合并前从功能分支打、合并后从 main 打，把「CI 已测过」的内容提前交到用户手里试用。`/release` 正式发版不需要再加机器验收（main 已被 CI 持续验证），人工验收已内化在「试用 → 满意 → 触发发版」的过程中。自动预发布（auto-rc）是「把 CI 测过的内容自动交到用户手里」的自动化，**不是「替用户决定满意」**——它自动化的是供料，不碰发版裁决权（正式发版永远由用户触发，机器门禁与人工门禁的分工不变）。
