# 测试包构建与人工验收

本文件是 dev-workflow 第 6 步的完整规矩。位置固定：**全量测试通过之后、合并回 main 之前**。

## 为什么需要人工验收（机器门禁之外的第二道门）

- 全量测试管**客观回归**（改 A 坏 B），人工验收管**主观满意**（做出来的是不是用户想要的样子）。用例是需求的机器翻译，翻译本身可能有漏——尤其界面、体验、文案这类难以完全用例化的维度，用例全绿 ≠ 用户满意。
- **合并前返工代价最小**：不满意就在 dev 上继续改；一旦合进 main 再返工，要走新一轮完整分支流程。
- 很多项目源码跑通 ≠ 安装包能用（打包过程的依赖剪裁、资源路径、运行时环境差异），所以验收对象是**构建出来的测试版安装包**，不是源码直跑——这同时把「可打包性」验证前置了（本地构建成功本身就验证了 `/release` 阶段才可能暴露的打包问题，风险前移）。

## 构建规矩（五条）

1. **在 dev 的 worktree 里构建**：验收对象是这个分支的成果，从 main 构建没有意义。按项目发布工艺来（vsce package、npm pack、tsc 打包等）。
2. **测试版本标识**：测试包必须有别于正式版的版本号（如临时加 `0.0.0-test` 或 prerelease 后缀），构建完把源码里的临时版本号**还原干净**——不占正式版本号，与「功能分支不 bump 版本号」纪律一致。
3. **产物放 tmp/**：worktree 的 `tmp/` 目录（遵守 tmp-dir-for-artifacts 规则），worktree 删除时一起清。
4. **不打 tag、不发 GitHub Release**：测试包只服务本次验收，不进发版流水线。
5. **与运行版隔离规则不冲突**：`runtime-dev-isolation` 禁的是 npm link、常驻直跑开发源码当运行版；这里是验收动作的一次性安装，验收完被卸载或被正式版覆盖，性质不同，合规。

## 验收动作

用户安装测试包实测 + 按 `pending/<需求名>/requirement.md` **逐条核对**。开发 Agent 在一旁待命，准备接收反馈。

## 验收不通过：一个循环，不是一个终点

验收反馈分两类，处理路径不同：

- **实现不符合需求**（功能没做完、行为和文档不一致、体验不满意）→ dev 上改 → **重新跑全量测试**（不是只跑改过的部分——改动可能碰坏别的地方，这正是全量回归的意义）→ 重新构建测试包 → 请用户复验。循环直到两道门都过。
- **需求本身要变**（用户看完实物想改主意）→ 走「终止上报」通道：用户找测试方（Hopper）改 requirement.md 和用例、同步进项目，dev 分支重新对齐后继续。需求变更不经这条通道、开发 Agent 自己揣摩着改，会做成「没人定义过的需求」。

## 验收期间 main 变动的处理

验收可能跨小时甚至隔天，期间 main 若被动了（测试方同步用例、别的分支合并），**合并前的硬校验会拦住**（见 `references/merge-discipline.md`）。返工口径：重新 merge main 进 dev → 重跑全量 → 绿了之后，main 新进的只是用例或文档 → 验收结论延续，直接合并；进了别的功能代码 → 请用户快速复验再合并。

## main 的语义闭环

走完本流程后 main 的语义：**main = 机器门禁（全量测试）+ 人工门禁（用户验收）双重通过的集合**。`/release` 发布的就是这个集合的快照，发版环节不需要再加验收。
