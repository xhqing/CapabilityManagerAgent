# PR 合并纪律：三重门、验收冻结、并行 PR

本文件是 dev-workflow 第 7 / 9 步的完整论证。核心命题分两层：**合并进 main 的内容 == 远端 CI 测过的内容**（合并不引入任何未经测试的变更，由 CI 独裁）；**正式发布的内容 == 用户使用验收过的内容**（发版以试用满意为前提，由用户把关）。角色分立：用例定义权归测试 Agent（测试先行、开发只读），代码实现权归开发 Agent，合并裁决权归机器门禁，发布裁决权归用户。旧版本地裁决版（2026-09-07 ~ 2026-09-21）靠「超集校验 + 本地快进合并」保证第一层；2026-09-21 起改由「分支保护 + required checks + 平台 merge 语义」在远端**结构性**保证——不是「应该等 CI」的纪律，是「绕不过」的平台机制；同日二次修订把人工验收从合并环节移到发版环节（体验即验收），三次修订引入测试 Agent 主通道与测试先行（详见 test-cases.md）。

## 三重门结构

1. **分支保护（结构性门）**：main 的合并条件由 GitHub 强制，配置清单——
   - Require a pull request before merging（禁止直推 main）；
   - Required status checks：CI job 必须绿，否则 merge 按钮不可用；
   - Require branches to be up to date before merging（合并前分支须包含最新 main）；
   - 只允许 squash 合并（禁 merge commit / rebase 选项，保持 main 线性历史）；
   - 不开管理员 bypass——所有内容一律 PR，无特权通道；用户自己的手动修改同样走 PR（GitHub 网页编辑自动开 PR）。
   - **首次启用顺序（防死锁）**：先让 ci.yml 经 PR 进 main（此时保护未开或未设 required checks，PR 可合并），再开分支保护并把 CI checks 设为 required。反过来先开保护 + required checks，则第一个 PR 的 check 从无成功记录、永远不满足，流程死锁。
   - 配置通道：GitHub 网页（Settings → Branches / Rules → Rulesets），或 `gh api`（rulesets API / 老式 branch protection API），经用户同意后代配置。
2. **远端 CI（机器门）**：`pull_request` 触发，GitHub 干净环境跑全量（项目单元测试 + `test-cases/` 全量 + 类型检查，三段式口径见 test-cases.md）。**为什么裁决在远端而不止本地**：本地测试可被环境差异与漏跑稀释，且本地「绿」与「可合并」没有结构绑定；CI + required checks 把两者在平台层面钉死——本地全量测试保留为预检（快速反馈，红灯本地修省往返），CI 是权威。
3. **用户使用验收（人工门，发版门禁——不是合并门禁）**：CI 绿 ≠ 用户满意。用例是需求的机器翻译，翻译有漏（界面、体验、文案），但这些维度的把关不放在合并环节（等人工会卡住集成节奏），而是放在发版环节：用户安装功能分支 / main 的**预发布版本实际使用一段时间**，体验即验收；试用满意才正式发版（`/bump` + `/release` 由用户主动触发，触发即验收通过的表达）。验收是过程不是瞬时门禁——需要时间暴露问题，这正是复杂项目 CI 慢的窗口期先预发布的价值：等 CI 与试用的两段时间天然重叠。

## 合并后修复循环（试用发现问题的处置）

试用中发现问题不回退已合并的 PR（main 持续前进是正常状态，CI 保证每步都绿），而是走修复循环：建 fix 分支 → 修 → 本地全量 → push + 建 PR + enable auto-merge（CI 绿合并）→ 递增预发布号（rc.2）再试用。循环到用户满意为止，正式发版随之推迟。为什么不在合并前等人（旧模式）：等待窗口内集成停滞、并行分支互相积压；而试用反正需要时间（天级），把试用放在 CI 跑的窗口期并行展开，等 CI 绿时试用已开始——发现问题的修复循环更快接上。

注意主客观分工：CI 管「客观回归」（改 A 坏 B，用例能断言）；试用管「主观满意」（好不好用、是不是想要的，用例难以表达）。两层各自把关各自的，互不替代。

## squash merge 的树等价（物理基础）

GitHub squash merge 产生的新 commit，其树（全部文件内容）== PR head 的树——squash 只把分支上的多个 commit 压成一个提交，不改任何文件内容。因此「CI 在 head 上跑绿 + squash 合并」⟹「main 收到的内容 == CI 测过的内容」。旧版靠快进合并（main 指针直接移动、树逐字节相同）保证；新版靠平台 merge 语义保证——树等价不变，保证者从本地 git 操作换成 GitHub 的合并实现。为什么选 squash：main 保持线性历史（延续旧版快进传统）；功能分支的中间过程 commit 不进 main。

## 并行 PR：up-to-date 要求与 update-branch 循环

多个 PR 并行时，A 合并后 B 的 up-to-date 条件失效（B 不再包含最新 main）→ 平台挡住 B 的合并 → 在 B 分支 `git fetch origin && git merge origin/main` 后 push → CI 对新 head 重跑 → 重新可合。这是并行的结构性代价，平台自动执法、无本地硬校验步骤。A 带来的冲突此时暴露——早对齐冲突小，这正是第 9 步「合并后立即把 origin/main 同步回其它活着的 worktree」的原因。测试方的用例同步 PR、杂事 PR 合并后同样触发这个循环：只动用例 / 文档时功能代码没变，用户已有的验收结论延续；进了别的功能代码时按下方口径复验。

## 合并被挡后的处置口径

update branch、CI 绿之后自然合并；CI 红则修到绿。up-to-date 挡住时看 main 新进的是什么，用于判断对试用中预发布版本的影响：

- **只是用例或文档**（测试方同步 PR、杂事 PR）→ 功能代码没变，不影响试用结论；
- **进了别的功能代码** → 用户试用中的预发布版本与 main 现状出现差异，下个预发布号（rc.N+1）自然带上这些内容，用户重新拉新版继续试用即可。

## 门禁分工的精确含义

机器门（分支保护 + CI）保证的是：**合并这个动作不引入任何未经测试的变更**；合并后 main 上每次 push 的 CI 让回归防护网持续生效——漏网问题在 main 上立刻红，可被下一个修复 PR 快速定位。

人工门（试用 + 发版决定）保证的是：**正式发布的版本是用户使用验收过的**——试用发现的问题走修复循环消化在发版之前，正式版不带已知的主观不满意。

两层合起来**不**保证「软件没有 bug」——测试覆盖度、用例质量是出用例方的责任边界；试用覆盖不到的维度（没试到的操作路径、环境差异）也可能藏问题。表述时保持这个精确度，避免过度承诺。
